# Agent 运行环境的硬边界

一句话原则：**agent 的 shell 不是用户的 shell，也不是 CI**。它有一组不写在任何报错里的规则：调用之间进程会被回收、文件系统可能是 overlay、回环地址是私有的、每条命令有截止时间。把这些当物理定律，不要当 bug 去绕。

## 1. 工具调用结束 = 该调用派生的所有子进程被回收

- **现象**：起了个服务/浏览器，下一条命令就 `Connection refused`，进程数归 0。
- **实测过的无效绕法**（五种，全部失败）：前台直接起、关掉沙箱再起、`nohup ... &`、托管后台任务、PowerShell `Start-Process` 想脱离进程树。前四种随调用结束回收；后台任务还额外跑在**隔离命名空间**里，前台调用根本看不见它。
- **最阴的一种误判**：`nohup ... & sleep 5; 检查进程` —— 检查通过了，于是判定"服务活着"。**那次存活发生在同一次调用内**，下一条命令时它已经不在了。跨调用存活的判据只能是：**隔一次调用再看还在不在**。
- **对策**：需要长期存活的进程（真实浏览器、数据库、dev server）**由用户在自己的桌面会话里启动**（桌面双击一个 `.bat` 即可），agent 只负责连接它。凡是中途要等人（扫码、验证码、人工确认）的流程，都适用这条。
- **判定**：agent 自己起的进程只适合"在本次调用内开始并结束"的活（单次截图、单批查询）。

## 2. 沙箱回环与 overlay 临时盘

- **现象**：主机上明明监听 `127.0.0.1:9222`，沙箱里连不上；生成的截图/文件当次能 `ls` 到，下一条命令就 `No such file or directory`。
- **根因**：沙箱有**独立回环栈**（`127.0.0.1` 不是主机的），以及**写时复制的临时文件系统 overlay**（调用结束丢弃）。
- **对策**：跨边界要访问的东西，写进**真实项目目录**（不是临时目录），端口/服务由用户侧提供；需要访问主机回环时走提升权限的执行方式。
- **判定**：同一条读取命令在两次调用里结果不同 = 命中 overlay；`netstat`/端口探测与主机不一致 = 命中独立回环。**别在这两类环境里调试"服务为什么连不上"**，先确认在不在同一侧。

## 3. 纯本地操作报出"外联错误"：是沙箱，不是权限，也不是磁盘

- **现象**：执行 `cp` / `ls` / `rm` 这类完全不碰网络的命令，报 `502` 或 `getaddrinfo ENOTFOUND <某个内部域名>`。
- **根因**：沙箱的外联探针拦下了这条命令，报错信息来自探针而不是你的命令。**错误文本里的域名与任务毫无关系**——那是最容易带偏方向的地方（会开始怀疑网络、DNS、代理）。
- **对策**：认症状下结论：**本地文件操作 + 网络类报错 = 沙箱拦截**，用提升权限的方式重跑同一条命令即可。不要去"修网络"。
- **判定**：把同一条命令换个不涉及网络的写法（或提权重跑），若立刻正常，归因确认。

## 4. 单条命令有截止时间

- **现象**：命令跑到一半被掐（输出到一半就断 / exit 空），看起来像脚本崩了；全盘 `find`、`du`、循环 192 个目录这类操作最容易撞上；磁盘快满时元数据操作还会整体变慢。
- **根因**：每条调用有超时上限，且**超时与失败在输出上很难区分**。
- **对策**：**一次调用只做一步**，宁可多调几次；预计长的显式走后台任务；递归扫描降维（`-d1` 逐层、定点扫，不要一上来全盘）；超过 2 分钟无输出就换定向策略，别硬等。
- **判定**：怀疑超时的命令，先用一个缩小版（限制范围/条数）跑一遍——小样能过、全量挂，就是时长问题而不是逻辑问题。这一步花 10 秒，省掉一轮误诊。

## 5. 长任务必须假设"会被外力打断"

- **现象**：跑到一半，被操作的对象（浏览器窗口、外部程序）被人关了，整批活白费、状态丢失，只能从头再来。
- **对策（三件套，缺一都出事）**：
  1. **进度落盘**：每完成一项就写状态文件（`done` 计数、已处理 ID 清单），且**写完再往下走**；内存里的进度不算进度。
  2. **重连而不是终止**：连接型自动化要有"探活 → 重连 → 从状态文件续跑"的循环；实测第 3、4 次重连就能自愈。
  3. **不要在 `finally` 里 close 整个连接/应用**：正常收尾会顺手把宿主程序关掉，下一次重连就得从头起，而且中途失败时它同样执行——把"失败即中断"升级成"失败还顺手拆了现场"。只关自己开的 page/会话，别关宿主。
- **判定**：跑长任务前先问一句"**中断后再启动，会从哪一步继续？**"答不出来就说明还没做完设计。

## 6. 环境能力会跨会话漂移，别用上一次的清单推断这一次

- **现象**：昨天能 push 今天 `Connection reset`；同一台机器白天判"沙箱可非交互 push"，当晚被证伪；给 MCP 服务加了新工具，当前会话里却看不见（要重启客户端才加载）；换个 shell，PATH 解析到的解释器就不一样（见 runtime-resolution-and-abi）。
- **对策**：**环境能力每次实测**，一次探测 3 秒，误判一次赔一轮。把探测结果写进当次结论里（"刚才测过：API 通、push 不通"），别写成"这个环境能 push"。
- **附带**：新会话/首轮可能工具面更小（未挂上的 MCP、未授权的能力）。工具不在时先确认是否只是未加载，而不是断言"本环境不支持"。

## 7. 越出工作区的写入：那是等待授权，不是失败

- **现象**：命令被拦下并提示需要批准（写目标目录在工作区外、访问凭据、对外发布类动作）。
- **对策**：**说明你要做什么、为什么，然后重试同一条命令**——授权通过后原样再跑是最短路径。不要为了绕开拦截而改写目标路径、拆成多步、或换工具做同一件事：那既慢，又正好绕过了那层保护存在的原因。
- **判定**：区分三种拦法——**报错说路径/权限不行**（真失败，改做法）、**提示需要批准**（等授权，重试原命令）、**沙箱探针式外联报错**（§3，提权重跑）。三者症状相似、修法完全不同。

## 8. 自动化批量改动的两道计数闸

- **现象**：脚本"跑完了、没报错"，实际上漏改了 40 处，或者把不该改的 3 处一起改了。批量替换尤其危险，因为它成功和空转的返回值一样。
- **对策**：脚本必须自己吐出两个数：
  - **MISS**：应命中而未命中的锚点数（先 Grep 数出现次数，与预期一致才允许 `replace_all`）；
  - **DUP**：锚点不唯一的处数（`old_string` 带前后各 1–2 行上下文，短片段必然撞上重复）。
  收尾再跑一次"应当为 0"的复扫（例如全文 grep 旧写法，命中数必须是 0），把复扫结果当验收证据，而不是把脚本退出码当验收证据。
- **判定**：任何"改动是否生效"用第三方读法复核（重新读文件 / `git diff --stat`），不要信写入工具返回的 `Successfully edited`。

## 9. 子代理与他人自述：只认 diff

- **现象**：委派出去的任务回来报"已完成并验证通过"，但落盘状态里根本没那些改动；或者它做的是"打算做"而不是"做了"。
- **对策**：**自述不是证据**。接住任何"完成"之前，跑一次客观对账：`git status --short`、`git diff --stat`、文件计数、断言脚本，逐项对上再认。同理，跨会话续接时先测当前状态，不要相信摘要里的"已完成"。
- **附带（同一失效的镜像面）**：委托搜索/审读时给的范围太窄会漏，太泛会带回不可信的结论。**子代理给的每条引用都要抽验**——本项目实测中，"某个字段不存在"的结论只是因为写查询的人用了单数形式（`Battery` vs `Batteries`），**结论是假的，工具用法是真的**。

## 10. 备份与临时文件落在项目里，会被工具链当成内容带走

- **现象**：`.old-<日期>` 备份残留、`__pycache__`、调试用 profile 目录（内含真实 Cookie）、会话 `.session.json` —— 被同步脚本扇到多台客户端、被 `git add -A` 卷进提交、被打包进构建产物。
- **根因**：**同步/打包/提交的规则是"目录里的都算内容"**，它不区分"这是她的备份"。而带凭据的目录恰好就常放在项目里。
- **对策**：① 备份/临时文件放项目**外**的专门目录（或写进 `.gitignore` **和**同步排除清单）；② 动被多端同步的共享目录前，先确认扇出范围——一处改动可能同时改到 5 台客户端；③ 提交前 `git show --stat HEAD` 扫清单；④ **凭据类目录必须进排除清单，且这一条要在真正执行同步之前验证，不是之后**。
- **判定**：对准备交付的目录做一次显式禁词扫描（用户名、机器名、账号 handle、内网端口、密钥文件名），并且**同时跑一条必然命中的对照查询**。命中 0 而对照查询也命中 0，说明是扫描写错了，不是内容干净（见 shell-quoting-and-path-forms §9）。

## 复用信号

"起了又死了""文件不见了""端口拒连""本地操作报网络错""这条命令怎么老被掐""它说做完了""备份怎么被推上去了" → 全部先归到"这是环境边界还是我的逻辑错"，再决定要不要改代码。
