# Agent 运行环境的硬边界

一句话原则：**agent 的 shell 不是用户的 shell，也不是 CI**。它有一组不写在任何报错里的规则：调用之间进程会被回收、文件系统可能是 overlay、回环地址是私有的、每条命令有截止时间。把这些当物理定律，不要当 bug 去绕。

## 1. 工具调用结束 = 该调用派生的所有子进程被回收

- **现象**：起了个服务/浏览器，下一条命令就 `Connection refused`，进程数归 0。
- **实测过的无效绕法**（五种，全部失败）：前台直接起、关掉沙箱再起、`nohup ... &`、托管后台任务、PowerShell `Start-Process` 想脱离进程树。前四种随调用结束回收；后台任务还额外跑在**隔离命名空间**里，前台调用根本看不见它。
- **最阴的一种误判**：`nohup ... & sleep 5; 检查进程` —— 检查通过了，于是判定"服务活着"。**那次存活发生在同一次调用内**，下一条命令时它已经不在了。跨调用存活的判据只能是：**隔一次调用再看还在不在**。
- **对策**：需要长期存活的进程（真实浏览器、数据库、dev server）**由用户在自己的桌面会话里启动**（桌面双击一个 `.bat` 即可），agent 只负责连接它。凡是中途要等人（扫码、验证码、人工确认）的流程，都适用这条。
- **判定**：agent 自己起的进程只适合"在本次调用内开始并结束"的活（单次截图、单批查询）。

- **复测更正（2026-09-21）：这条不是物理定律，是运行时属性。**本会话在同一台机器的另一种执行面上实测：**正常退出**（rc=0）的调用里起的后台进程，隔了 4 次调用、6.5 分钟后**仍然在**——`nohup sleep 900` 与裸 `& sleep` 两支都活着，PowerShell `Start-Process` 分出去的 `cmd.exe` 也活着；`setsid` 那一支当场就没有进程，原因是这个 shell **根本没有 `setsid`**（`command -v setsid` → `MISSING`），不是"它被回收了"。上面那五种绕法全失败的读数来自另一执行面（沙箱侧），不能拿来预测这一面。
- **根因**：调用结束时是否回收子进程，是**执行面**（进程树／作业对象怎么处理派生进程）的性质，不是 shell 的固有规律；本机这一面实测"正常退出的调用不回收它的后台子进程"。所以本条的正确用法是**每次都探**，而不是把任何一面的规律移植到另一面。
- **判定（据上改写）**：跨调用存活的判据仍然是"隔一次调用再查还在不在"，但**两种结果都是有效信息**：查到了 = 这一面不回收，那就别重复起、并且要负责收尾；查不到 = 命中本条。**用"上次会被回收"省掉这次探测，是本条最常见的误用。**
- **附带（本轮我自己踩的坑，恰好是本包的看家案例）**：第一次探活我把 `tasklist //FI "PID eq <号>"` 写在 `{ ... }` 命令组里，转义被吃掉 ⇒ tasklist 一个字都没输出，`grep -c .` 得到 **0**，于是我当场判定"那个进程没了"。改用干净的 `tasklist //FI "IMAGENAME eq cmd.exe"` 再单查同一 PID，它**活着**，配套的 `PING.EXE` 也在跑。**"进程不在了"与"我的查询没响应"在 stdout 上完全同形**——跨调用探活这条判定命令自己必须带正控（同面查一个必然在的 PID），否则它给的正是假结论。
- **验证于**：Windows 11 家庭中文版 10.0.26200.9457（zh-CN）· Git Bash 5.2.37(1)-release(x86_64-pc-msys) · Windows PowerShell 5.1.26100.9444 · git 2.53.0.windows.2 · 2026-09-21
  （读数：起进程的那次调用 13:31:56 正常退出，13:32:21 与 13:38:22 两次跨调用探活均 ALIVE；`Start-Process` 分出的 `cmd.exe` 在 13:41 的干净 `tasklist` 里仍在，`PING.EXE` 同列在位；`command -v setsid` → MISSING。**未测到的部分**：那五种绕法在沙箱侧的失败读数本轮未复跑，故原条目保留、不升为通用定律。）

## 2. 沙箱回环与 overlay 临时盘

- **现象**：主机上明明监听 `127.0.0.1:9222`，沙箱里连不上；生成的截图/文件当次能 `ls` 到，下一条命令就 `No such file or directory`。
- **根因**：沙箱有**独立回环栈**（`127.0.0.1` 不是主机的），以及**写时复制的临时文件系统 overlay**（调用结束丢弃）。
- **对策**：跨边界要访问的东西，写进**真实项目目录**（不是临时目录），端口/服务由用户侧提供；需要访问主机回环时走提升权限的执行方式。
- **判定**：同一条读取命令在两次调用里结果不同 = 命中 overlay；`netstat`/端口探测与主机不一致 = 命中独立回环。**别在这两类环境里调试"服务为什么连不上"**，先确认在不在同一侧。

- **复测（2026-09-21，本执行面两条判据都不成立）**：
  - overlay 临时盘：第 N 次调用往 `/tmp/<固定名>.txt` 写一行，第 N+1 次调用 `cat` 取回同一行；项目目录内的文件跨 6 次调用持续可读。⇒ 本面没有"调用结束丢弃写入层"这件事。
  - 独立回环栈：第 N 次调用里 `bind()` 到 `127.0.0.1:<随机端口>` 并 `listen()`，那次调用**正常结束**（不是后台挂着），第 N+1 次调用 `connect()` 成功且 `getpeername()` 报回的端口就是当初那个；同一时刻本机侧其它进程监听的端口在本面也连得上（HTTP 200）。⇒ 本面与主机共用回环栈。
- **所以这条的正确用法是先花三步确认自己不在这一类面上**：① 上一步写的文件这一步还在不在；② 上一步起的监听这一步连不连得上；③ 端口探测结果与主机侧一致不一致。三条全"在/连得上/一致" ⇒ 本条不适用，别拿"沙箱连不到主机 9222"去解释一次失败（那是把方向直接带偏）。
- **验证于**：Windows 11 家庭中文版 10.0.26200.9457（zh-CN，ACP 936）· Git Bash 5.2.37(1)-release(x86_64-pc-msys) · Python 3.12.10 · 2026-09-21
  （跨调用监听读数：监听于第 1 次调用、连上于第 2 次调用；`/tmp` 探针为同批两次调用。**未测到的部分**：本面没出现被沙箱化的那次调用形态，故原文两种症状只能记为"未命中"，不是"不存在"。）

## 3. 纯本地操作报出"外联错误"：是沙箱，不是权限，也不是磁盘

- **现象**：执行 `cp` / `ls` / `rm` 这类完全不碰网络的命令，报 `502` 或 `getaddrinfo ENOTFOUND <某个内部域名>`。
- **根因**：沙箱的外联探针拦下了这条命令，报错信息来自探针而不是你的命令。**错误文本里的域名与任务毫无关系**——那是最容易带偏方向的地方（会开始怀疑网络、DNS、代理）。
- **对策**：认症状下结论：**本地文件操作 + 网络类报错 = 沙箱拦截**，用提升权限的方式重跑同一条命令即可。不要去"修网络"。
- **判定**：把同一条命令换个不涉及网络的写法（或提权重跑），若立刻正常，归因确认。

- **复测（2026-09-21，本执行面未复现，且扫描带正控）**：一次调用里跑纯本地操作 300 余项（建 300 个文件、`cp` 单文件、`cp -r` 整目录、`ls | wc -l`、`rm -rf`、`find -type f | wc -l`、`du -sh`），stdout+stderr 合并落文件后按 `502|ENOTFOUND|getaddrinfo|proxy|ECONN|network` 扫：**0 命中**、整批 `rc=0`；**同一份 grep** 打到注入了两行真实外联报错（`… returned error: 502` / `getaddrinfo ENOTFOUND …`）的副本上命中 **2**。⇒ 0 是"真没有"，不是"我的扫描不响"。
- **推论（给这条定适用边界）**：本面没有那层外联探针，所以"本地文件操作 + 网络类报错 = 沙箱拦截"只能当**在有探针的面上成立的正判据**用；**不能**反过来在本面拿"报了网络错"当线索。本面最有用的对照就是这次读数本身：整套本地操作零网络字样 ⇒ 你不在那一类面上，去找真原因。
- **验证于**：Windows 11 家庭中文版 10.0.26200.9457（zh-CN）· Git Bash 5.2.37(1)-release(x86_64-pc-msys) · GNU grep 3.0 · 2026-09-21
  （301 项建文件 → `rm -rf` → `ls` 计 0；正控 2 命中/负控 0 命中同批取。）

## 4. 单条命令有截止时间

- **现象**：命令跑到一半被掐（输出到一半就断 / exit 空），看起来像脚本崩了；全盘 `find`、`du`、循环 192 个目录这类操作最容易撞上；磁盘快满时元数据操作还会整体变慢。
- **根因**：每条调用有超时上限，且**超时与失败在输出上很难区分**。
- **对策**：**一次调用只做一步**，宁可多调几次；预计长的显式走后台任务；递归扫描降维（`-d1` 逐层、定点扫，不要一上来全盘）；超过 2 分钟无输出就换定向策略，别硬等。
- **判定**：怀疑超时的命令，先用一个缩小版（限制范围/条数）跑一遍——小样能过、全量挂，就是时长问题而不是逻辑问题。这一步花 10 秒，省掉一轮误诊。

- **复测（2026-09-21）：本运行时给出的是另一种形态，不是"被掐"。**拿一条已知要 130 秒的命令（`sleep 130`）在默认阈值下跑：**没有**"输出到一半就断 / exit 空"——120 秒时工具面回报"超过阈值、已转入后台"并给一个任务号，命令**继续跑完**：13:40:11 起、13:42:21 止（正好 130 秒），stdout 完整落进任务输出文件，收尾 rc=0，另有一条完成通知送达。
- **所以这条的真坑不是进程被杀，是两个读数错觉**：① 工具结果里看不到这条命令的最终输出，容易被当成"失败了/崩了"，于是**重跑**——而它其实还在跑，重跑就是双写；② 它继续占着进程与文件句柄。本轮另一次就是 `... | tee`：后台子进程继承了管道的写端，`tee` 永远等不到 EOF，一条本应 2 秒的调用被拖到超时。
- **对策（补两条）**：**先读那个输出文件再决定要不要重跑**；"还在不在跑"用进程列表判，不要凭工具结果里缺输出推断。管道类命令里起后台进程时，**必须**把它的 stdout/stderr 重定向离管（`>/dev/null 2>&1`），否则管道会把整次调用拖死。
- **验证于**：Windows 11 家庭中文版 10.0.26200.9457（zh-CN）· Git Bash 5.2.37(1)-release(x86_64-pc-msys) · 单次调用默认阈值实测 120 秒 · 2026-09-21
  （130 秒样本：超时 → 转后台 → 跑完 rc=0，全程 130 秒；`tee` 拖死那次为同会话独立样本。**未测到的部分**：显式设更长阈值的分支未测；"全盘 `find`/`du` 撞上限"这两类原场景本轮未复跑。）

## 5. 长任务必须假设"会被外力打断"

- **现象**：跑到一半，被操作的对象（浏览器窗口、外部程序）被人关了，整批活白费、状态丢失，只能从头再来。
- **对策（三件套，缺一都出事）**：
  1. **进度落盘**：每完成一项就写状态文件（`done` 计数、已处理 ID 清单），且**写完再往下走**；内存里的进度不算进度。
  2. **重连而不是终止**：连接型自动化要有"探活 → 重连 → 从状态文件续跑"的循环；实测第 3、4 次重连就能自愈。
  3. **不要在 `finally` 里 close 整个连接/应用**：正常收尾会顺手把宿主程序关掉，下一次重连就得从头起，而且中途失败时它同样执行——把"失败即中断"升级成"失败还顺手拆了现场"。只关自己开的 page/会话，别关宿主。
- **判定**：跑长任务前先问一句"**中断后再启动，会从哪一步继续？**"答不出来就说明还没做完设计。

- **复测（2026-09-21）：把"进度落盘"这一件做成真的剂量反应，中断是外部下的手**。200 项批处理（每项 = 落一个产物文件），跑到一半由父进程 `kill()`：
  - 状态文件版：被杀时产物 68 个、完成清单 68 条，**差值 0** —— "写完状态再往下走"这个顺序在真实中断点上成立；重启后只处理剩下的 132 项，4.3 秒收尾。
  - 内存版对照：同样被打断，产物 69 个**还在**，但没有任何清单 ⇒ 重启后 200 项从头再做（6.3 秒）。
  - ⇒ 判据要换掉一个直觉：**别用产物文件个数当进度**。"69 个产物躺在那儿"看起来像进度，实际是 0 条可续跑状态；而且被打断那一项的产物本身还可能是半截的（本轮未测半截产物的具体形态）。可续跑的判据是"有一份完成清单，且清单条数 == 产物数"。
- **未测到的部分**：三件套里第 2、3 件（连接型自动化的"探活 → 重连 → 第 3~4 次自愈"、以及"别在 `finally` 里 close 宿主"）依赖外部程序会话，本轮在本面未复跑，原条目保留原状。
- **验证于**：Windows 11 家庭中文版 10.0.26200.9457（zh-CN）· Python 3.12.10 · 外部 `kill()` 打断点实测 68/200 与 69/200 两组 · 2026-09-21

## 6. 环境能力会跨会话漂移，别用上一次的清单推断这一次

- **现象**：昨天能 push 今天 `Connection reset`；同一台机器白天判"沙箱可非交互 push"，当晚被证伪；给 MCP 服务加了新工具，当前会话里却看不见（要重启客户端才加载）；换个 shell，PATH 解析到的解释器就不一样（见 runtime-resolution-and-abi）。
- **根因**：agent 的运行边界是**按调用/按会话**发的，不是按机器发的——网络策略、凭证、PATH、已挂载的 MCP 工具面都可能在你两次命令之间被人改过或根本没继承上一次的结果。
- **对策**：**环境能力每次实测**，一次探测 3 秒，误判一次赔一轮。把探测结果写进当次结论里（"刚才测过：API 通、push 不通"），别写成"这个环境能 push"。
- **附带**：新会话/首轮可能工具面更小（未挂上的 MCP、未授权的能力）。工具不在时先确认是否只是未加载，而不是断言"本环境不支持"。
- **判定**：开工第一件事跑固定三探，输出直接抄进当次结论，环境能力只有"刚才测过"这一种证据：
  ```bash
  curl -s -m 8 -o /dev/null -w 'api=%{http_code}\n' https://api.github.com   # 取不到三位数 = 外连未通
  python -c "import socket;print('tcp=',bool(socket.create_connection(('github.com',443),timeout=8)))"
  for c in git node python curl; do printf '%s ' "$c"; command -v "$c" || echo MISSING; done   # 必须逐个点名
  ```
  逐条 `command -v` 是硬要求：`command -v a b c` 只要有一个在就返回 0（见 `silent-failure-triage §2`）。MCP 工具"加了却看不见"的判定不在终端里：查**当前会话**的工具清单里有没有那个名字，没有就按未加载处理（重启客户端），别据此断言"本环境不支持"。

- **复测（2026-09-21）：三探给出真实读数，并给这条加一个新的漂移轴——同一台机器、同一分钟内，两条路由给出相反答案。**`curl https://api.github.com` **直连 = 200**，**走本机出口代理 = 403**（配额被共享出口 IP 花完，机制见 `github-network-and-api-fallback §9`）；`tcp github.com:443 = True`；`command -v` 逐条：`git` / `node` / `python` / `curl` 在位，**`jq`、`pwsh` 均 MISSING**。⇒ 探测结论必须**连着路由一起写**，"API 通不通"这种写法本身就是不合格结论。
- **附带（同一条本轮又踩实一次）**：`command -v git <不存在A> <不存在B>` 只打印 git 那一行、**rc=0**——一次性多点问，会替缺失的工具盖章；逐条点名才是判定。
- **验证于**：Windows 11 家庭中文版 10.0.26200.9457（zh-CN）· git 2.53.0.windows.2 · Node v24.18.0（`<Node 安装目录>`）· Python 3.12.10 · curl（Git for Windows 自带）· 2026-09-21
  （直连 200 与代理 403 在同一分钟取；TCP 探到 `True`；`jq`/`pwsh`/`setsid` 三条 MISSING 为同批读数。**未测到的部分**：MCP 工具面跨会话增减本轮未测，那条只保留原状。）

## 7. 越出工作区的写入：那是等待授权，不是失败

- **现象**：命令被拦下并提示需要批准（写目标目录在工作区外、访问凭据、对外发布类动作）。
- **对策**：**说明你要做什么、为什么，然后重试同一条命令**——授权通过后原样再跑是最短路径。不要为了绕开拦截而改写目标路径、拆成多步、或换工具做同一件事：那既慢，又正好绕过了那层保护存在的原因。
- **判定**：区分三种拦法——**报错说路径/权限不行**（真失败，改做法）、**提示需要批准**（等授权，重试原命令）、**沙箱探针式外联报错**（§3，提权重跑）。三者症状相似、修法完全不同。

- **复测（2026-09-21）：本执行面没有这道闸 ⇒ 三分法要按"谁在拦"分，不能按"报错长什么样"分**。同一批越界动作，从解释器里直接发：
  - 写用户主目录下一个探针文件：**成功**（回读一致，随后自删，本机无残留）；列 `~/.ssh` 目录项：**成功**（只列名字，没读任何私钥内容）。
  - 写 `C:\Program Files\…`：**真失败** —— `PermissionError errno=13`；写不存在的卷 `Z:\…`：**真失败** —— `FileNotFoundError errno=2 / winerror=3`（"系统找不到指定的路径"）。这两种等不来批准，只能改做法。
  - `bind()` 一个本地端口、读凭据目录：都不触发任何拦截。
- ⇒ 授权闸在**工具调用层**（我发起的那次 Bash/Write 会被要求批准），**不在 OS 层**：动作一旦被我写进脚本里跑，那道闸就不存在了。所以这条只在"我被提示需要批准"这个症状上成立；**绝不能反推成"越界动作总会有人来拦"** —— 本面实测不会。真正兜底的是"要不要做这件事"的判断本身，脚本层没有任何东西替我省掉它。
- **验证于**：Windows 11 家庭中文版 10.0.26200.9457（zh-CN）· Python 3.12.10（非管理员令牌）· 2026-09-21
  （errno=13 与 errno=2/winerror=3 两条为同批读数；主目录探针写后已删并复查不存在。）

## 8. 自动化批量改动的两道计数闸

- **现象**：脚本"跑完了、没报错"，实际上漏改了 40 处，或者把不该改的 3 处一起改了。批量替换尤其危险，因为它成功和空转的返回值一样。
- **对策**：脚本必须自己吐出两个数：
  - **MISS**：应命中而未命中的锚点数（先 Grep 数出现次数，与预期一致才允许 `replace_all`）；
  - **DUP**：锚点不唯一的处数（`old_string` 带前后各 1–2 行上下文，短片段必然撞上重复）。
  收尾再跑一次"应当为 0"的复扫（例如全文 grep 旧写法，命中数必须是 0），把复扫结果当验收证据，而不是把脚本退出码当验收证据。
- **判定**：任何"改动是否生效"用第三方读法复核（重新读文件 / `git diff --stat`），不要信写入工具返回的 `Successfully edited`。

- **复测（2026-09-21）：两道闸各给出可用读数，并暴露出第三条更阴的闸。**temp 夹具 6 行、维护者以为该有 4 处锚点：朴素 `str.replace` **rc=0、零自证**；带闸的写法自己吐出 **MISS = −1**（实际 5 处，比预期**多**一处）与 **DUP = 1**（同一行两处）。⇒ 闸不只抓"漏"，也抓"你以为少了"——两个方向都得停手核对。
- **第三条闸（本轮新暴露）**：改完之后全文复扫旧写法 **命中 0**，看着正是本条要的验收；但夹具第 3 行本来就是少一个字符的变体，它**原样残留**——旧写法的**变体**不在复扫词表里，于是"0 命中"把漏改吃得干干净净。**验收判据必须是"预期条数 == 实际条数"，不是"命中 0"。**
- **验证于**：Windows 11 家庭中文版 10.0.26200.9457（zh-CN）· Python 3.12.10 · 2026-09-21
  （6 行夹具、预期 4 / 实际 5 / 同行重复 1；MISS、DUP 由脚本自吐，残留变体经逐行读回确认。同批还做了 §9 的双读数对账。）

## 9. 子代理与他人自述：只认 diff

- **现象**：委派出去的任务回来报"已完成并验证通过"，但落盘状态里根本没那些改动；或者它做的是"打算做"而不是"做了"。
- **对策**：**自述不是证据**。接住任何"完成"之前，跑一次客观对账：`git status --short`、`git diff --stat`、文件计数、断言脚本，逐项对上再认。同理，跨会话续接时先测当前状态，不要相信摘要里的"已完成"。
- **附带（同一失效的镜像面）**：委托搜索/审读时给的范围太窄会漏，太泛会带回不可信的结论。**子代理给的每条引用都要抽验**——本项目实测中，"某个字段不存在"的结论只是因为写查询的人用了单数形式（`Battery` vs `Batteries`），**结论是假的，工具用法是真的**。

- **复测（2026-09-21）：两条"客观读数"当场互相矛盾——这才是本条真正要防的东西。**temp 新 `git init` 仓库（这台机器上 `core.autocrlf = true` 是全新仓库的默认，git 2.53），对同一文件做四种写入，两侧读数是：
  | 写入动作 | `git status --short` | `git diff --stat` |
  |---|---|---|
  | 字节完全相同的原样重写 | 空 | 空 |
  | 只 `touch` 改 mtime | 空 | 空 |
  | **内容等价、行尾 CRLF→LF**（本轮我自己造成的） | **报 ` M <file>`** | **空** |
  | 真改一行 | 报 ` M <file>` | ` 1 file changed, 1 insertion(+), 1 deletion(-)` |
  ⇒ **"status 里有 M" 不等于"改动生效"**：内容经行尾规范化后等价，但工作树字节变了，status 就报 M，而 diff 侧一个字都不报。唯一说真话的地方在 **stderr**（那句 `LF will be replaced by CRLF the next time Git touches it`），脚本里一个 `2>/dev/null` 就把它抹掉了。
- **判定（补强）**：对账**同时**取 `status --short` 与 `diff --numstat`；两者不一致 ⇒ 先怀疑规范化层（行尾、权限位、符号链接），**不要**按 status 报的条数声称"改了几处"，也不要把 stderr 丢掉。
- **验证于**：Windows 11 家庭中文版 10.0.26200.9457（zh-CN）· git 2.53.0.windows.2（全新 scratch 仓库，`core.autocrlf=true`）· Git Bash 5.2.37 · 2026-09-21
  （四格读数全部实跑：no-op 与只改 mtime 两支均为空，这就排除了"stat 缓存脏了必然报 M"的替代解释。**未测到的部分**：`--ignore-cr-at-eol` 只在这一支上验过一次，未做多种行尾组合。）

## 10. 备份与临时文件落在项目里，会被工具链当成内容带走

- **现象**：`.old-<日期>` 备份残留、`__pycache__`、调试用 profile 目录（内含真实 Cookie）、会话 `.session.json` —— 被同步脚本扇到多台客户端、被 `git add -A` 卷进提交、被打包进构建产物。
- **根因**：**同步/打包/提交的规则是"目录里的都算内容"**，它不区分"这是她的备份"。而带凭据的目录恰好就常放在项目里。
- **对策**：① 备份/临时文件放项目**外**的专门目录（或写进 `.gitignore` **和**同步排除清单）；② 动被多端同步的共享目录前，先确认扇出范围——一处改动可能同时改到 5 台客户端；③ 提交前 `git show --stat HEAD` 扫清单；④ **凭据类目录必须进排除清单，且这一条要在真正执行同步之前验证，不是之后**。
- **判定**：对准备交付的目录做一次显式禁词扫描（用户名、机器名、账号 handle、内网端口、密钥文件名、**真实姓名与内部称呼**），并且**同时跑一条必然命中的对照查询**。命中 0 而对照查询也命中 0，说明是扫描写错了，不是内容干净（见 shell-quoting-and-path-forms §9）；对照为何会"看着写了却不响"，两支成因见 silent-failure-triage §13。

- **复测（2026-09-21）：这道闸当天真的在出站路径上跑了一次。**对 3 棵待推提交树逐棵建导出面，10 类禁词**各自**注入正控 ⇒ 三棵树均"正控盲区类 = 0"；净面唯一命中类是出口端口号，逐条判定为**非新增**（其中一处正是扫描器自己的正则字面量——门禁的脏样本也算公开物）。之后网络侧另取真相：`ls-remote` 一回、公网原文逐文件哈希比对 6/6 相同。
- **本轮新增一条"对照为什么会不响"，而且是两个相反方向**：
  - **恒假**：探进程存活时把 `tasklist //FI "PID eq <号>"` 的转义写坏 ⇒ 输出空 ⇒ `grep -c .` 得 0 ⇒ 差点把"活着"报成"没了"（见 §1 附带）。
  - **恒真**：判断行尾时写 `grep -c <回车>`，那个模式在命令传递中被吃成**空模式** ⇒ 对每一行都匹配 ⇒ 148 行报 148，看起来完全像"整个库都是 CRLF"，据此我差点把已经写坏的行尾"合法化"。**空模式 = 恒真**，与"扫描器没生效"同形。
  ⇒ 两个方向都不能靠"看数字合不合理"排除，只能靠**字节级读回**（`od -c`、`tr -dc <回车> | wc -c` 这类直接数数节的写法）加**同面必然命中的对照**。
- **验证于**：Windows 11 家庭中文版 10.0.26200.9457（zh-CN）· git 2.53.0.windows.2 · Python 3.12.10 · GNU grep 3.0 · 2026-09-21
  （两处自踩都由字节级读回推翻：`od -c` 显示首行只有 `\n`、`tr -dc '\r' | wc -c` = 0，于是"库是 CRLF"当场作废；门禁那一轮的逐类正控数、净面命中类与公网哈希结果均记录在当日黑板条目里。）

## 11. 共享状态工具的写通道报错：先读链尾，再决定要不要重试

- **现象**（本机实测）：往一个带哈希链的协作黑板（MCP server + 后端 SQLite）写 `evidence`，MCP 侧连报两次 `MCP error -32603: did not complete`，**连只读的 `check` 也报同一个错**。看起来像"共享库坏了"，最自然的动作是重试写入——而那正是会落两条重复条目的动作。
- **根因**：`-32603` 是 JSON-RPC 的"内部错误"笼统桶，它只描述**这一次调用没走完**，不区分挂在哪一层：MCP 进程、桥接层、后端库。三层挂任一，你看到的都是同一句话。而且**写请求超时不等于写没发生**——落库与返回是两件事。
- **对策**：① **换通道读，不要换工具写**：用另一条独立通道（同一后端的 CLI，或直接只读打开那份 DB）把状态读回来，一次就能分清"通道坏"还是"库坏"。② **写失败后先查链尾再重试**：链尾最后一条 seq 就是你的写入前基线；内容已在链上 = 已落库，别再补一遍。③ 兜底通道要**事先跑通过**再依赖它（本次用的 CLI 与 MCP 打的是同一个库、同一套校验）。④ 解释器/原生模块那类坑（同一份 CLI 换 Node 版本就起不来）见 `runtime-resolution-and-abi §3`，别在通道排障里重复怀疑。
- **判定**：
  ```bash
  <node> <cli> timeline | tail -1      # 记下最后一条 seq，作为写入前基线
  <node> <cli> timeline | tail -3      # 写失败之后立刻再读一次
  ```
  - 基线 seq 未变、且链上没有你那条内容 → 真没写进去，换通道写一次，写完再读链尾确认。
  - 链上已经出现你那条内容（哪怕 MCP 报的是错）→ **假失败**，收工，不要重写。**这一支本次未观察到**：实测的是相反情形——两次 `-32603` 之后链尾没有多出任何条目，所以"库里到底写没写"必须靠读来定，不能靠报错文案推。列为规则是为了让你**先读再写**，而不是为了声称它发生过。
  - 同一动作 CLI 成功、MCP 报 `-32603` → 结论是**这个客户端不可达**，不是共享服务坏了：不要重启服务、不要改库、不要把这条写成"服务故障"上报。
  - 同族假象：**光连上 MCP 不等于登记成功**——在线列表/心跳往往要等你写下第一条内容才出现，用"它连上了"推断"别人能看见我"会误判。
- **验证于**：Windows 10.0.26200 · Git Bash `GNU bash 5.2.37(1)-release (x86_64-pc-msys)` · Node v24.18.0（`<Node 安装目录>\node.exe`）· better-sqlite3 ABI 137 · 2026-09-17

## 12. 派活归属存在两个地方，而"看谁在干"的那个视图不读你写进去的那张表

- **现象**（本机实测）：用 `assign <任务> <身份>` 把一张长期卡派给 4 个协作方，四条命令**全部回显成功**（`Assigned #4 to … — notification left in their inbox`），归属表里也确实有 4 行。可是任何一个协作方跑聚合视图 `status` 看"未完成的活"那一栏，这一条显示的仍是 `(unclaimed)`——看起来像没人管。更绕的是同一份数据在另一个视图里是对的：明细看板 `tasks` 显示 `80% ←<身份甲>,<身份乙>,<身份丙>,<身份丁>`（协作方身份名此处略，与结论无关）。**两次读，两个结论。**
- **根因**：归属写进**两张地方**，读视图各取一张。`assign()` 落的是多对多的 `task_assignees`（源码里那句是 `INSERT OR IGNORE INTO task_assignees …`），随后**无条件**再调 `message()` 投一条收件箱、`append()` 追加一条时间线；而任务行上的 `claimed_by` 只有 `claim` 会写。聚合视图渲染那行的代码是 `t.claimedBy ? '← ' + t.claimedBy : '(unclaimed)'`——**它压根没查 assignees 表**（同一个包里另有把两处并起来读的函数 `activeAgentsOnTask()`，只是这个视图没用它）。所以不是写失败，是汇总视图漏了一张表。
- **对策**：① **别把归属字段当送达信号**——派活真正会被对方读到的是它自动投进收件箱的那条 message，送达自查看 `outbox`；② 对外说"谁在做这张卡"时读**明细看板**或直查 `task_assignees`，不要引用聚合视图那一行；③ 想让一张卡有单一持有人，另外走 `claim`（它才写 `claimed_by`，且别人已 claim 时会报 CONFLICT）；④ **重复 assign 修不好显示**：那句是 `OR IGNORE`，重派只会多投一条收件箱 + 多落一条时间线，归属行数不变、显示照旧，而回显仍是"Assigned"——典型的"命令成功但事情没成"。
- **判定**：
  ```bash
  <node> <cli> status | grep -A3 "Open work"    # 聚合视图怎么说
  <node> <cli> tasks   | grep -i <编号>          # 明细看板怎么说（按编号，别按 key）
  <py> -c "import sqlite3 as s;print(s.connect('<库目录>/board.db').execute('select agent,assigned_by,assigned_at from task_assignees where task_key=?',('<key>',)).fetchall())"
  ```
  - 表里有行、`tasks` 里有 `←名字`、`status` 里却写 `(unclaimed)` → **视图漏表**，不是写失败：不要再补一次 assign，改用 ② 的读法拿真相。
  - 反例校验（把"我的 key 没出现在输出里"当结论之前必做）：明细看板打印的是**标题不是 key**，`tasks | grep <key>` 必然命中 0 且退出码 1——这是"按列表里没有的字段去 grep"造成的**假阴性**，不是卡丢了。换一条**必然命中**的查询（按编号、或按标题里的一个词）跑一遍，命中了才说明前一条是扫描写错。同族见 `silent-failure-triage §2`。
  - 顺带一条同源的显示层坑：`inbox` 返回体里的 `readAt` 取的是消息行上的**全局**列，不是本身份的已读台账，所以"我读过没"只看它**有没有出现在列表里**，别看那个字段。
- **验证于**：Windows 10.0.26200 · Git Bash `GNU bash 5.2.37(1)-release (x86_64-pc-msys)` · Node v24.18.0 · Python 3.12.10 · 2026-09-17

## 13. 共享工作树里，门槛脚本分两次编辑＝别人在你中间那一步调用到半成品

- **现象**（本机实测）：协作者回报"你那个 `scripts/check.py` 曾短暂坏掉，跑 stats 报 `NameError: name os is not defined`"。可我事后打开看是好的，我自己也刚跑通过。**同一条命令，他坏、我好、现在都好。**
- **根因**：门槛脚本不是我的私有工具，是**所有并发协作者都会调用的活依赖**，而它放在同一份共享工作树里。我当时分两次编辑：第一次把新逻辑写进去（开始用 `os.path`），第二次才补 `import os`。**未提交的编辑对所有人立刻可见**——git 只在 commit 之后才给你隔离，工作树里根本没有"我的改动"和"别人的改动"之分。那几百秒里任何人跑门槛，拿到的都是半份程序。
- **对策**：① 改共享的门槛/工具脚本，**一次写完再落盘**（单条整体写入，或先在**项目外** temp 里改完、验证过再整份复制进共享区），绝不用"先改引用、后补定义"的多步顺序直接落在共享工作树；② 落盘后**立刻自测一次**再去做别的事，把窗口压到最短；③ 别人报"工具忽然坏了"，**先查自己工作树有没有未提交的半改**（`git status --porcelain -- scripts/`），不要第一反应怀疑对方环境或对方的解释器版本——那会把你的半成品记成别人的 bug；④ 门槛脚本刻意保持**单文件 + 只用标准库**，依赖面小，坏时的影响面才小。
- **判定**：
  ```bash
  git status --porcelain -- scripts/            # 有 M ⇒ 此刻共享工作树里的门槛不可信，谁的运行结果都别当证据
  git hash-object scripts/check.py              # 报故障的人附上这个值，和维护者手里的一比
  git log -1 --format=%h -- scripts/check.py    # 已提交版本；与工作树哈希不同＝读到的是半成品
  ```
  - `git hash-object`（工作树）与 `git rev-parse HEAD:scripts/check.py`（已提交）**不一致** → 有人正在改，先协调再重跑，别急着下"这工具坏了"或"我环境坏了"的结论。
  - 两值相同却仍然 `NameError` → 真 bug，提 issue，不是编辑窗口造成的偶发。
  - 关键区分：这类故障**没有稳定的复现路径**（窗口一关就好了），所以"我这儿是好的"完全不构成反驳；判定只能靠上面的版本比对，不能靠当场重跑一次看运气。
- **验证于**：Windows 10.0.26200 · Git Bash `GNU bash 5.2.37(1)-release (x86_64-pc-msys)` · Python 3.12.10 · git 2.53.0.windows.2 · 2026-09-17

## 14. 用 A 组件的配置去断言 B 组件的行为：一次真实的错判

- **现象**（本机实测）：看到派活守护的配置里写着 route: { workbuddy: codex }（agent-bridge/daemon.config.json），于是我断言「派给 workbuddy 的黑板任务都会转交 codex，所以它收不到」，并进一步写成「workbuddy 不存在自主巡逻黑板」。实际相反：我派的那张卡，workbuddy 自己回了执（带完整读数），而且它自己把卡标成了 cancelled；另有多轮 e2e 里 workbuddy 自己 claim / complete / message。那条断言是错的，差点被写进永久的教训库。
- **根因**：把「某组件的配置」当成了「另一个组件被观测到的行为」。那行配置（daemon.js 里 execAgent = enabledAgents.includes(to) ? to : route[to]）只描述派活守护自己起哪个无头面，根本没有描述 workbuddy 自身的输入输出能力。两个组件、两层语义，中间那条「谁触发谁、谁真的执行」的链没验。更危险的是配置读起来很像证据（有文件、有字段、有明确取值），于是推断跳步时不会触发任何警报；而「我没看到它做」与「它做不到」在配置里长得一模一样。
- **对策**：
  - 断言某实体的能力或行为之前，手上至少要有一条该实体自身的观测：它自己发的消息、它自己做的状态变更（claim/complete/文件写入）、它的进程或日志。配置只用来解释「某个组件的意图」，不能拿去证明「另一个实体的行为」。
  - 跨组件时先把链画出来：A 的配置 → A 的动作 → B 的输入 → B 的输出。缺哪一段就去测哪一段；测不了就写「未核实」，不要用链条上游的静态字段补下游行为结论。
  - 特别警惕两类代理信号：①路由表 / 白名单 / 映射表（描述组件自己的动作选择）；②别人写的说明文档（描述意图，不是运行结果）。它们都不能代替「该实体自己发出的记录」。
  - 反向也成立：别人用同类代理信号给你下结论时，先要一条你自己的观测（如「你在什么序列号上回执过」）再接受或反驳。
- **判定**：先拿一条该实体自己的记录，再下结论。两种机械读法都行：
  - 直读黑板库：node -e 借助 node:sqlite 以 readOnly 打开 <黑板>/board.db，在 timeline 表上按 actor=<实体名> 计数（0 次才允许说它做不到）；
  - 或读链：octoboard CLI 的 timeline 子命令输出里 findstr 该实体名，看它有没有自己发起的 message / claim / complete / task-status 行。
  - 本例读数：actor=workbuddy 在时间线上有多行（回执 message、claim、task-status cancelled、complete）⇒ 它有自主接单能力；而 daemon.config.json 的 route 只描述守护自己的执行选择，两者作用域完全不同。
  - 反向自检：若你只读过配置文件、没读过该实体自己的记录，结论就一律降级为未核实。本例还留了一个可查痕迹：被误判的那张卡面上曾写着不存在自主巡逻黑板，该句已撤回。
- **验证于**：Windows 11 家庭中文版 10.0.26200 · Node v24.18.0（直读 sqlite）/ octoboard CLI · 2026-09-26
