# 陈旧产出的五层缓存 + 一层数据快照

一句话原则：**"改动没生效"从来不是一个故障，而是五层缓存里某一层在起作用**（另有 §8 一层数据快照，不是缓存、症状相同），它们的**表象完全相同**（界面/产物是旧的）。所以不要一上来就再改一遍代码——那会在正确的代码上叠加错误的改动。逐层证明"改动到达了这一层"，第一层断掉就停在那里修。

## 0. 分层模型

```
源码 → 构建产物 → 运行中的服务 → 客户端渲染 → 已部署的线上
 ①       ②            ③             ④            ⑤
```
每层配一个**独立判据**（下面各节给出）。顺序不能跳：跳层会误诊，且会把某一层的好改动改成迎合另一层的错误版本。

①–⑤ 是"改了但没到达"；§8 的存储层不在这条流水线上（它是**读到的旧**，不是**改了的旧**），症状与①–⑤ 无法区分，五层排完仍不对再查它。
§9 的同步/拷贝层同样**不在这条流水线上**：它不是"某一层的缓存挡住"，而是**拷贝这一步本身落错了位置**——旧内容仍在真身里、新内容在嵌套副本里。症状与 ①–⑤ 无法区分，故排在构建层之后、服务层之前判一次（只需一条 `Test-Path <目标>\<名>\<名>`）。

- **状态**：复盘条目（纯分层框架节，无判定命令可复测；各层判据见 §1-§6 的实测/复盘）
- **验证于**：Windows 11 家庭中文版 10.0.26200 · Windows PowerShell 5.1.26100.9444 · 2026-09-21（只覆盖本次新增的 §9 一句，其余内容非本轮实测）

## 1. 源码层：先证明"真的改了"

- **判据**：在源码里搜一个**新代码独有的特征串**（新色值、新类名、新文案），而不是搜"改过的那个函数"。搜不到 = 源码根本没改，后面四层都是白排。
- **两个常见假成功**：① 编辑工具返回 `Successfully edited` 但改动被同批并行 Edit 覆盖（见 silent-failure-triage §10）；② 改的是 A 副本、跑的是 B 副本（junction/软链/多检出，`stat -c '%d:%i'` 比 device+inode 才认得出同一份）。

- **验证于**：Windows 11（10.0.26200）· Git Bash bash 5.2.37（git 2.53.0.windows.2）· 2026-09-17（实测：经 junction 访问与源路径 `stat -c '%d:%i'` 返回同一 inode，证实"认得出同一份"判据可区分副本与同份）

## 2. 构建层：增量构建会漏掉整类产物

- **现象**：源码有、构建"成功"、产物里却没有新样式。
- **根因**：增量构建对某些资产**不重新生成**（典型是 CSS chunk），只跑 `npm run build` 不够。
- **对策**：**先删构建缓存目录再全量构建**（`.next`、`dist`、`out`、`__pycache__`、`.turbo`、`.cache` 视工具链而定）。判据统一用一条：
  ```bash
  grep -rl "<新特征串>" .next/ dist/ 2>/dev/null    # 产物里搜不到 = 断在这一层
  ```
- **同层陷阱（构建报错而不是没生效）**：**备份/临时文件放在项目内**，构建工具（tsconfig 的 include、type-check）会扫到**残缺副本**（缺同目录被 import 的模块）而直接报错，看起来像"我的改动把项目改坏了"。备份一律放项目外；报错时第一步就是找项目内的 `.old`/`backup`/`副本` 目录。

- **判定**：`grep -rl "<新特征串>" .next/ dist/ 2>/dev/null`——有输出且退出码 0 = 产物已含新字节（不在这层）；退出码 1 空输出 = 断在这一层（实测：含标记的产物命中 rc=0，不含的目录空输出 rc=1）。
- **验证于**：Windows 11（10.0.26200）· Git Bash bash 5.2.37（git 2.53.0.windows.2）· 2026-09-17

## 3. 服务层：旧进程还在监听端口

- **现象**：构建产物是新的，抓下来的页面却是旧的。
- **根因**：旧 server 进程（可能由桌面应用自己拉起）仍占着端口，新构建从未被服务过。
- **判据与对策**（按端口找主人，别按进程名猜）：
  ```powershell
  Get-NetTCPConnection -LocalPort <端口> | Where-Object State -eq 'Listen' |
    Select-Object -Expand OwningProcess
  Get-Process -Name "node" | Select-Object Id, StartTime     # 有多个 = 有更早的旧进程
  ```
  杀掉监听进程后再重启，然后**重新验证 §4**（不要杀完就当修好了）。
- **判定**：`StartTime` 早于你本次构建时间 = 命中。

- **验证于**：Windows 11（10.0.26200）· Windows PowerShell 5.1.26100.9444 · 2026-09-17（实测 127.0.0.1:<端口> → OwningProcess=<pid> → cozedrive-core，StartTime 在本次会话之前，判据成立）

## 4. 渲染层：Service Worker 是最大元凶

- **现象**：服务器返回的 HTML/CSS 明确是新的，客户端仍显示旧界面。
- **根因**：`sw.js` 用 **cache-first** 拦截了静态资源请求，缓存不失效它就永远命中旧副本——服务器多新都无关。**它连导航请求一起拦**，所以旧的不只是子资源：`index.html` 本身也是旧的那一份。
- **实测形态**（本地自建 cache-first 站点；服务端全程 `Cache-Control: no-store`，好让"旧"只可能来自 SW）：源上 CSS 已含新色、不含旧色，客户端仍是旧色，页面里那个版本标记也仍是旧值；`caches` 里那一版存的确实是旧字节。
- **最佳判别器（花 10 秒，直接定位到层）**：**换一个干净的浏览器状态打开同一地址**（无头侧 = 新建 browser context；日常 = 无痕窗口或另一台浏览器）。干净侧一次导航就是新的（新色 + 新版本标记），带 SW 那侧仍是旧的 ⇒ 服务端和构建两层都不用碰。桌面应用旧、浏览器新 = 同一判据的日常形态。
- **只清 HTTP 缓存无效**：`Network.clearBrowserCache` 之后仍是旧色旧版本标记——SW 的 CacheStorage 不是 HTTP 缓存，两层的清理动作不能互相顶替。
- **对策（有效的是让旧 SW 失效，不是清目录）**：把 `sw.js` 里的 `CACHE` 版本号 +1，并在 `activate` 里删掉非当前版本的缓存。实测旧缓存被删、新版本生效、渲染翻色。**但接管时机是异步的，刷新次数不固定**：同一测法三轮读数分别是"第 2 次翻色""第 3 次翻色""3 次内不翻" ⇒ **不要写成"刷两次就好"**；要么轮询到读数真的变了为止，要么主动 `registration.update()`（官方推荐的触发方式，实测能让它在下一次导航前就位）。
- **两个顺序约束（复测后改写；原来的两处说法都不成立）**：
  1. **运行中删 SW 的缓存目录 = 白删**，但**不是因为删不掉**。实测 Chrome 还开着时 `Remove-Item -Recurse -Force` 打 `Default\Service Worker\CacheStorage`：**rc=0、整目录消失**（`-ErrorAction Stop` 也不报错）——"文件被占用删不掉"这一条在这层未复现。真正的坑是删完没有效果：当前页面继续用内存里的渲染，再导航一次该目录被**重建**、旧内容又缓存回去（实测 5 个文件 → 删光 → 重建 2 个文件，缓存里仍是旧值）。
  2. **`SilentlyContinue` 吞的是错误文本，不是退出码；失败形态是"部分删除"**。真正被占用的文件确实删不动，实测 `Default\Cache` 10 个文件删剩 1、`Default\Local Storage\leveldb` 5 删剩 4（`000003.log` 和 `LOCK` 留下），而 stdout 与 stderr **全空**（一行报错都没有），但 **rc=1**。所以判据必须两条一起看：**rc=0 且计数归零**；只看"有没有报错文本"必然以为清了。应用退出后同一批全部 rc=0 且删空。
- **顺带（这条仍未复测，别再当已验证用）**：窗口在启动瞬间闪旧色块，往往是宿主配置里硬编码的 `backgroundColor`，不是缓存；查"哪里还留着旧值"时要连这类常量一起扫。本机无 Electron 宿主可测；用 Chrome 进程级 `--default-background-color=RRGGBBAA` 试过两次等价物（alpha `00` 与 `FF`），截图与不带参数**逐像素相同**，说明该开关在新版无头下不是可用等价物 ⇒ 保持未复测。

- **验证于**：Windows 11 家庭中文版 10.0.26200.9457 · Chrome 153.0.8010.48（`--headless=new`，Node v24.18.0 裸 CDP，隔离 profile）· Windows PowerShell 5.1.26100.9444（删除读数）· Pillow 12.3.0（截图像素计数）· 2026-09-22
  （本地自建 cache-first 站点与无头 Chrome，不出网；除上面标注的 `backgroundColor` 一条外，本节读数均为本轮实测。两次独立运行给出同一形状。）

## 5. 部署层：推上去了 ≠ 线上是新的

- **现象**：仓库/构建产物确认是最新的，线上 URL 却返回旧内容或子资源 404。
- **常见三种，判据各不同（本轮逐一取到真实读数）**：
  - **平台还在用旧构建 / 构建还没跑完**（切换构建源/分支后尤其明显，子资源整片 404）：判据是平台侧的构建端点，不是刷新页面。实测 `GET /repos/<owner>/<repo>/pages` 回 `{status:"built", build_type:"legacy", source:{branch:"gh-pages"}}`；`GET .../pages/builds/latest` 回 `{status, commit, created_at, duration}`，其中一次真实构建 **duration=47.178 秒** ⇒ "推完立刻刷 URL"必然读到旧内容，要轮询而不是连刷。
    - **轮询判据必须接受两种终态**：同一仓最近 30 条构建历史里状态取值只有 `built`(24) 与 **`errored`(6)**；另取一仓 100 条同样只有 `built`(86) / `errored`(14) —— 拼写是**两个 r**。只等 `built`、把其它值当"还在构建"，就会在一条已经失败的构建上无限轮询；正确写法是 `built` 或 `errored` 都停，再按 `errored` 去查构建日志。
    - **但先读 `/pages` 的 `build_type`，它决定 builds 端点可不可信**：实测取值有两种——`legacy` 与 **`workflow`**（不是 `github-actions`）。**`workflow` 形态下绝不能拿 `pages/builds/latest` 当终态**：实测一个 `build_type:"workflow"` 的站点上该端点照样秒回 `{status:"built", created_at:"2023-07-17T16:47:42Z", duration:46721}`，而该仓同一天（09-22）的真实部署是一条 `completed`/`success` 的 Actions run；它的 builds 历史 100 条里最旧 2022-05-25、最新就是 2023-07-17，**切换构建方式之后一条都没进** ⇒ "轮询到 built"在这种站点上是必然的**假完成**（先前那句"workflow 站点没有 pages/builds 序列"不成立：另一种形态是直接 404，实测另一仓 `/pages` 回 `{build_type:"workflow", status:null}`、`builds/latest` → `404 Not Found`；两种表现都不可用 builds 端点）。正确取数：`GET /repos/<o>/<r>/actions/runs?per_page=100` 里 **`head_sha` 等于你刚推的那个 commit** 的那条 run，`status=completed` + `conclusion=success` 才算完；workflow 名字不固定（实测见到 `pages build and deployment`、`Deploy site`、`Deploy`），所以**按 `head_sha` 匹配，不要按名字过滤**。
  - **仓库可见性**：私有仓库的裸文件对外是 **404**，而"推送成功"是真的（见 github-network-and-api-fallback §7 末条）。实测形状：一个**文件确实存在**（鉴权 `GET /repos/<o>/<r>/contents/` 读得到）的私有仓，未鉴权 `raw.githubusercontent.com/<o>/<r>/<branch>/<file>` 返回 **404**，与"该仓根本不存在"的 404 **同形、不可区分**；同一账号公开仓的 `README.md` 返回 **200**。⇒ 线上一片 404 而推送成功，第一嫌疑是可见性 / Pages 未开，不是构建坏了。
  - **URL 形态没对上**：托管路径与站点基路径（`/` 还是 `/docs`、子目录）不匹配时，首页可能像样而资源全 404。这一种**本地就能复现**，判据一条命令即可：把页面里每个 `href`/`src` 按 `new URL(引用, 页面URL)` 解析后逐个取状态码。实测（站点只挂在 `/docs/` 下）：页面 `/docs/` → **200**，根绝对引用 `/assets/abs.css`、`/img/logo.png` → **404**，相对引用 `assets/rel.css`（解析为 `/docs/assets/rel.css`）→ **200**。⇒ "首页像样、子资源整片 404"就是基路径没对上，改引用形态或改部署前缀二选一，不用怀疑构建。
- **读数自身的坑**：`000` 不是平台判决。实测同一个"不存在的仓库"URL 两轮分别给出 `http=000`（连接被重置，另见 `curl rc=56`）与 `http=404` —— 前者只是通道噪声；私有仓那条也是重试到第 1~3 次才拿到真码。⇒ 拿到 `000`/空码时**必须重试**，只有真状态码才算读数（失败重试与通道选择见 github-network-and-api-fallback）。
- **判定**：拿**平台侧的权威状态**（上面的构建状态端点 / 部署 API 返回）而不是浏览器行为来判"部署完成了没"。浏览器有它自己那层缓存（§4）。
- **仍未复测的部分**：**服务侧**「切换构建源/分支后平台仍拿旧构建对外服务（子资源整片 404）」这一形态本轮未复现——复测要拿自己的站点反复改 Pages 构建配置，本轮不新建托管站点、也不对任何仓库做写操作。已复现的是它的**读数侧同族**：站点切换构建方式后，`pages/builds/latest` 从此冻结在切换前那一刻并继续秒回 `built`（上面那条 workflow 读数）。⇒ 本节判据"平台说完成 ≠ 线上是新的"成立；但"平台真在用旧构建对外服务"的具体现场仍是复盘。

- **验证于**：Windows 11 家庭中文版 10.0.26200.9457 · Git Bash 5.2.37 · gh 2.97.0 + System32 的 curl 8.21.0（经 Python 3.12.10 子进程；真实公开仓与本机账号仓库的只读端点读数）· Node v24.18.0（本地基路径复现）· 2026-09-22
  （外呼全部只读，未对任何仓库做写操作；私有标识不进正文。Pages 端点那组读数当天测过两轮，第二轮换了候选仓重跑，字段值与计数逐条对上：`build_type` 两形态、`duration` 47178 / 46721、历史状态分布 30 条 = built 24 + errored 6、100 条 = built 86 + errored 14、workflow 站点 builds 冻结在 2023-07-17；未鉴权 raw 私有 → 404、不存在 → 404、本机公开仓 README → 200 亦为第二轮复现。）

## 6. 最终确认：要有一个真实渲染的证据

- **现象**：前五层的判据全过了，页面仍然不对——产物里有新字节、服务返回 200、平台说部署完成，视觉上是旧的样子。
- **根因**：前面五层全是**字符串匹配**，能定位但不能证明。"CSS 里有那个色值"和"页面看起来是那个颜色"之间还隔着优先级、覆盖、条件渲染三段路。
- **对策**：收尾固定一次真实渲染验证：实际打开页面 + 截图，用视觉（或视觉判据）确认结果，同时看控制台有没有报错。
- **实测的"字符串全绿、渲染全红"现场**：产物 CSS 返回 200、md5 随本轮改动重算得到 `3f380b80`、新色值确实写在文件里，**连 CSSOM 里都搜得到它**——而渲染仍是旧色，因为更高优先级的一条 `body.page { background: <旧色> }` 覆盖在上面。删掉那条覆盖规则，同一页面立刻翻成新色（一次改动同时让控制台 error 从 3 降到 0）。
- **两个必须知道的读数量纲**：
  - `getComputedStyle` 也还在**字符串层**：它读的是样式解析结果，会被优先级和条件渲染改写，不等于"屏幕上是什么"。真判据是**截图像素计数**——实测覆盖未修时图里旧色 `(192,57,43)` 有 **367116** 像素、新色 **0**；修掉后新色 `(39,174,96)` **367703**、旧色 **0**。
  - **CSSOM 的 `cssRules[].cssText` 会把 `#27ae60` 序列化成 `rgb(39, 174, 96)`**：拿十六进制串去搜 CSSOM 得到的零命中是**定义性零**，不是"新值没进规则"。要按序列化后的形态搜（实测同一份 CSS：十六进制搜 = 搜不到，`rgb(...)` 搜 = 搜得到）。
- **判定**：两条都要，缺一不算收工——① CDP 截图（`Page.captureScreenshot`）拿到的是**这次改动之后**的图，并与基线**逐项比对**，比对要落在像素计数/像素差上，不是眼看；② 同一页面控制台无新增 error（实测：故意留一条抛错脚本 + 一个 404 子资源时 error 数 = 3，其中含 `NETFAIL net::ERR_ABORTED` 这种"不算 HTTP 状态但会留痕"的形态；清掉后同一页面 = 0）。**HTTP 200、DOM 里搜到了新文案、产物文件哈希变了，三者都不是渲染证据。**

- **验证于**：Windows 11 家庭中文版 10.0.26200.9457 · Chrome 153.0.8010.48（`--headless=new`，Node v24.18.0 裸 CDP）· Python 3.12.10 + Pillow 12.3.0（像素计数判读）· 2026-09-22
  （本地自建页面，新/旧色用两个不相关 RGB，像素计数直接从 PNG 文件统计；截图与基线逐张比对。另：为隔离"SW 陈旧"与"优先级覆盖"两种可能，本轮显式在无 SW 的干净 context 里测本节，并打印前置自检。）

## 7. 出问题回滚：一次回，不要逐个手改

- **对策**：改动前先建 git 基线（`git status --short` 确认干净，或记下已改文件清单）。要回滚时用 git **一次性**回（`git diff` 确认范围后针对性 `checkout -- <本次文件>`），不要逐个文件手工改回去——手工回滚会漏、会带回旧 bug，还会把"本次改动"和"顺手改的别的"混成一团。
- **注意**：`git checkout -- .` 这类全量丢弃会连别人/别的任务的未提交改动一起清掉，所以先记清单再动手（工作树是唯一可信副本，同 git-ref-plumbing-on-windows §3 的告诫）。

- **判定**：改动前 `git status --short` 记清单；回滚 `git checkout -- <本次文件>`；回完再 `git status --short`，只剩他人/别任务的改动才算干净（实测：改 f1.txt 后 ` M f1.txt`，checkout 后内容还原、status 空）。
- **验证于**：Windows 11（10.0.26200）· git 2.53.0.windows.2 · 2026-09-17

## 8. 存储层：只复制主文件去读一个 WAL 库，会静默读到旧事务

- **现象**（本机实测）：查一个协作任务库（MCP 服务 + 后端 SQLite）的当前状态。用 `cp <库>.db <临时目录>/snap.db` 复制一份只读打开——**能打开、能查、零报错**，只是读到的状态是旧的：`select max(seq) from timeline` 得 **508**，而同一时刻该库的真实值是 **582**；据此我判定「某张任务卡还没被认领、对方 86 分钟零反应」并写了一份分析。**真相是那张卡早已 `done` / 100%，对方一小时前就交了证据并回了消息。** 我落后 **74 个事件、16 条消息**。
- **根因**：**WAL 模式下最近提交的事务先落在 `<库>.db-wal`，不一定已回写主库**。`cp <库>.db` 只带走主库文件 ⇒ 快照里缺少 WAL 里那些已提交的事务，于是读到一个「自洽但过期」的旧状态。它不报错，是因为那份快照本身就是**一个合法的、完整的数据库**——只是时点更早。同族：读 `.db` 而不带 `-wal`/`-shm`；库放在会被单独抓主文件的同步/备份目录里；在 A 副本上跑了 checkpoint 后拿 B 副本当「刚才那份」。
- **对策**：① 要快照就**三个文件一起拿**：`cp <库>.db <库>.db-wal <库>.db-shm <临时目录>/`——**每次都先 `ls` 看有没有 `-wal`**，别假设没有（本库就曾经真的没有，后来有了）；② 更稳的是走**库自己的读通道**（该库的 CLI / MCP / 直连），它会按正常语义把 WAL 一起读；③ 需要一份独立文件时才用 `VACUUM INTO '<新路径>'` 或 `.backup`——这两条是 SQLite 自带的、对 WAL 安全的导出方式，比 `cp` 正确；④ **凡「我没看到」的判断，先证明你的读通道能看见最新值**：拿一个你刚写入、已知最新的标记去查它（刚追的日志、刚写的行、`max(seq)`），查不到就说明你在读旧快照，此时**不得**对「对方没做」下结论。
- **判定**：用 Python 自带的 `sqlite3`（不依赖外部 CLI），一次列出「读者时点 / WAL 档位 / 我刚写的标记」三件事——
  ```python
  import os, sqlite3
  d = r"<库目录>"; f = os.path.join(d, "<库>.db")
  print("快照目录里的文件:", sorted(x for x in os.listdir(d) if ".db" in x))
  c = sqlite3.connect(f)
  print("journal_mode =", c.execute("pragma journal_mode").fetchone()[0])
  print("最新时点 =", c.execute("select max(seq) from <表>").fetchone()[0])
  ```
  两条判据：① `journal_mode` 读到 **`wal`** 而你的快照目录里**没有**同名 `-wal` ⇒ 命中本条；② 你刚写入的那条在快照里查不到、在直连库里查得到 ⇒ 你在读旧时点，凡基于它的「对方没做 / 还没发生」一律作废，重新读一遍再下结论。
- **验证于**：Windows 11 家庭中文版 10.0.26200.9457 · Git Bash 5.2.37 · Python 3.12.10（`sqlite3` 模块，SQLite 3.49.1）/ Node v24.18.0（`better-sqlite3`）· 2026-09-19

## 9. 同步/拷贝层：目标目录已存在时，`Copy-Item` 不覆盖它，而是钻进它里面

- **现象**（本机实测，六种写法）：同步脚本写 `Copy-Item <源>\skillA -Destination <目标>\skillA -Recurse -Force`，而 `<目标>\skillA` **已经存在**（上一轮同步留下的）。结果不是覆盖，而是：
  ```
  <目标>\skillA\SKILL.md            ← 内容仍是旧的（-Force 没碰它）
  <目标>\skillA\skillA\SKILL.md     ← 多出来的一份新副本
  ```
  **一次命令同时造成两种失效**：真身没更新 + 多一层嵌套。全程无报错、无警告，`$LASTEXITCODE` 为空（纯 PowerShell cmdlet 不设置它，读到的是上一支原生程序的残留值或空）。
  下游更糟：任何"按文件枚举条目"的采集端（`Get-ChildItem -Recurse -Filter SKILL.md`、按目录名建索引、扫全树收集技能）会把嵌套副本**当成一个独立条目**收进去——实测枚举结果从 1 条变 2 条。同一份内容从此有两个真相源，下一轮同步开始互相覆盖。
- **复测矩阵（同一次运行，同一对源/目标，只有写法不同）**：

  | 写法 | 目标里 `SKILL.md` 数 | 顶层那份内容 |
  |---|---|---|
  | `-Destination <已存在同名目录>` | 2 | 旧的 |
  | 同上，但源写 `<源>\skillA\`（带尾反斜杠） | 2 | 旧的 |
  | 源写 `<源>\skillA\*`（拷内容不拷壳） | 1 | 新的 |
  | 先 `Remove-Item <目标>\skillA -Recurse -Force` 再拷 | 1 | 新的 |
  | `-Destination <父目录>`（让它在父里对齐同名） | 1 | 新的 |
  | `-Destination <父目录>` 且源带尾 `\` | 2 | 旧的 |

  **"源路径带尾反斜杠就能避免嵌套"这条常见说法未复现**（第 2、6 行仍然嵌套）。落点只由 `-Destination` 指向的是"已存在的同名目录"还是"父目录"决定。
- **根因**：`Copy-Item` 的语义是"**把源作为子项放进 `-Destination` 指向的容器**"。当 `-Destination` 已经是一个存在的目录，它就是那个容器——于是源目录本身成为容器里的子项。`-Force` 只管"允许覆盖已存在的**文件**"，不改变落点选择，所以它既救不了旧内容、也拦不住嵌套。
- **对策**：
  ① 明确你要的是"对齐同名"还是"放进去"：想覆盖同名技能，写 `-Destination <父目录>`（且源**不带**尾 `\`），或写 `<源>\*` 指向目标目录本身；
  ② 同步的**幂等做法是先删后拷**，删除前先确认目标不是链接——`Get-Item -Force -LiteralPath <目标>` 的 `LinkType` 非空就停手（穿透删除的后果与写法见 `shell-quoting-and-path-forms §12`）；
  ③ 采集/枚举端**按名去重**，并对"同一技能名出现两次"直接判失败，而不是取第一个；
  ④ 同步的收口判据必须是**数量 + 内容**，不能是"命令没报错"：
  ```powershell
  $want = (Get-ChildItem <源> -Directory).Count
  $have = @(Get-ChildItem <目标> -Directory).Count
  $dup  = @(Get-ChildItem <目标> -Recurse -Filter SKILL.md).Count -ne $want
  if ($have -ne $want -or $dup) { "SYNC FAIL want=$want have=$have"; exit 1 }
  ```
- **判定**：同步后跑一条——
  ```powershell
  Test-Path <目标>\<条目名>\<条目名>          # True ⇒ 本条命中（嵌套已发生）
  (Get-Content <目标>\<条目名>\SKILL.md -Raw) -ne (Get-Content <源>\<条目名>\SKILL.md -Raw)
  ```
  第二个比较更硬：**没嵌套但没更新**（本条的第 1 行现场）只有它能抓到；`Test-Path` 单独用会漏。修完要两判据同时为假才算闭合。
- **验证于**：Windows 11 家庭中文版 10.0.26200 · Windows PowerShell 5.1.26100.9444 · 2026-09-21
  （实测：六写法矩阵见上；抛弃型 scratch 目录，源与目标均由探针自建。）
